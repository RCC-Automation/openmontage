# Checkpoints — what makes a film resumable

A checkpoint is a small JSON file at `projects/<id>/checkpoint_<stage>.json`
recording that a stage finished: which stage, its status, the artifacts it
produced, **whether the human approved it**, what it left unresolved, and when.

The distinction the whole thing rests on: **artifacts prove work happened; only
a checkpoint proves it was approved.** A song file on disk cannot tell you
whether anyone chose it, and a project full of correct artifacts still cannot
answer what stage comes next.

Related: [the loops](the-loops.md) · [measuring before believing](measuring-before-believing.md) · [the song](the-song.md)

## What we know

### Three things nothing else buys

| | Without checkpoints | With them |
|---|---|---|
| **Resume** | `get_next_stage()` reads checkpoints, so with none it answers `brief` — for a film with a locked score and six picked plates. What is done lives in prose a new session has to read and believe. | The session asks the project. |
| **Gate** | Exporting a half-picked film to the Builder is something an agent *remembers* not to do. | It is refused at write time. |
| **Send back** | Dailies finds a shot that drifted and there is nothing to reopen. | The superseded checkpoint is copied to `history/` first; the stage reopens with its record intact. |

### Both enforcement paths, run on this machine

Not asserted from reading the source — executed, 2026-08-30, on
`the-man-watches`:

```
$ checkpoint.py --stage brief --status completed
REFUSED
GATE VIOLATION: stage 'brief' requires human approval
(human_approval_default: true in the 'vrgdg-character-film' manifest)
but status='completed' was written without human_approved=True.

$ checkpoint.py --stage score --status completed --approved
REFUSED
PREREQUISITE VIOLATION: stage 'score' cannot advance;
incomplete or missing: ['brief', 'casting'].
```

The first is `write_checkpoint`'s gate check; the second is
`_enforce_stage_prerequisites`, which walks every predecessor and requires each
to be `completed` **and**, where the manifest gates it, `human_approved`.

Which stages gate is `human_approval_default` in the pipeline manifest. It is
binding — an agent may gate more strictly, never less.

### The order, and why it cannot be shortened

1. Run the stage, write the artifact to `artifacts/<name>.json`.
2. Write `--status awaiting_human`, show the human, **end the turn**.
3. The human approves or sends it back.
4. Write `--status completed --approved`.

Doing further pipeline work in the same response as step 2 is itself a gate
violation. The stop is the mechanism; without it the gate is a comment.

### `--open` is the highest-value field and the easiest to skip

A stage records what it did *not* settle, inside its own checkpoint. Casting on
`the-man-watches` carries:

> identity_stability across seeds is NOT measured — the manifest asks for it.
> Findability at 60 px was measured instead.

That is a success criterion the stage failed, written down by the stage that
failed it, surfaced on the status page under **Carried forward**, and readable
by a session that was never in the conversation. The alternative is a
clean-looking `completed` and a gap nobody finds until the shoot.

An honest `--open` is worth more than a tidy `completed`.

### The status page reads both, and never merges them

`projects/<id>/status.html` shows **checkpoint** (what the record claims) beside
**evidence** (what is on disk) for all ten stages. They are deliberately kept
apart: a disagreement means a stage ran outside the pipeline, or a checkpoint
was written for work that never landed. One green tick would hide exactly that.

It is generated by `scripts/project_page.py` from the project on disk, and
`scripts/checkpoint.py` regenerates it on every write, so it cannot drift.

## What it costs

Nothing measurable. A checkpoint write is one JSON validate plus one file
replace; the perceptible cost is the status-page regeneration, which re-encodes
the embedded media (a few seconds to about a minute depending on how many clips
the film has). Pass `--no-page` in a batch and regenerate once at the end.

## Traps

**Use the repo venv.** `.venv/Scripts/python.exe`. Checkpoint writing validates
every artifact against its schema and needs `jsonschema`, which the system
Python here does not have. `scripts/project_page.py` is deliberately
dependency-free and runs on either.

**A checkpoint embeds the artifact, so a stale artifact is embedded stale.**
Write the artifact first, then the checkpoint. Re-running a stage means
re-writing both.

**`CANONICAL_STAGE_ARTIFACTS` covers the nine legacy stage names, not this
pipeline's ten.** Only `scene_plan` has a *required* canonical artifact here.
The other stages will happily checkpoint carrying nothing, which validates
cleanly and tells you nothing later. `scripts/checkpoint.py` reads the
manifest's `produces:` list and loads those files itself for this reason, and
names in `metadata.declared_but_absent` whatever it could not find.

**Any artifact name in `ARTIFACT_NAMES` is schema-validated on the way in.**
Putting `song` in the artifacts dict as a *path string* rather than the object
fails validation. Embed the object.

**Retrofitting an approval is visible and should stay that way.** Where the
human approved before the record existed, `--approved-on` names when and how.
That is an honest trail for a one-off retrofit, not a way to write approvals the
script never witnessed.
