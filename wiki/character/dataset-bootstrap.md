The chicken-and-egg problem: a character LoRA needs 20–40 consistent images of a
person who does not exist yet, and you have one render you like.

**VRGDG already implements this loop** — and on this machine its character mode
silently degrades into the one thing our own measurements say does not work.

---

## What VRGDG ships, and why not to press its button

`VRGDG_LoraDatasetCreatorNodes.py` registers 11 routes under
`/vrgdg/lora_dataset/` — identity, concepts, image_prompt, caption, save_pair,
save_ic_pair, and more. Its `dataset_type='character'` flow drives an LLM to
invent a trigger word, expand concepts, and generate a set. The
first-image-becomes-the-anchor pattern is exactly right.

**Two blockers, both fatal as shipped:**

1. **The anchor never anchors.** On this machine the only local generators the
   Creator will drive are *text-only* Z-Image and Krea 2 — so every one of your
   20–40 images comes from a **description with no image conditioning**. Our own
   calibration says that is precisely the thing that produces a different woman
   each time.

2. **It hard-codes the pack author's filenames.** `workflowPayload()` in
   `web\VRGDG_LoraDatasetCreatorUI.js` sends `unet_name: 'z_image_turbo_bf16'`,
   `clip_name: 'qwen_3_4b'`, `vae_name: 'ae'` — **none of which exist here.** It
   fails on the first render, not the twentieth. This is the documented
   *"template model names are not yours"* trap, but worse: for ordinary build
   routes the payload overrides the template, whereas here the payload *is* the
   hard-coded wrong thing, in JavaScript, with no settings screen.

**Keep the valuable parts, drive the routes yourself over HTTP:** the identity
JSON prompt, the concept expansion, and the on-disk layout plus `dataset.json`
manifest the bundled trainer already understands. Substitute the generator.

## The loop that works here

**Use FLUX.2 Klein as the anchor engine.** It is on disk (3.79 GB), has a VRGDG
build route, renders in ~5 s, and we measured **0.93 identity on a matched
shot** — the best number on this machine.

```
1. Render one hero close-up. ArcFace-embed it -> the anchor.
2. For each concept: build_flux_klein_prompt(scene_prompt, images=[anchor])
3. ASSERT the built graph has 16 nodes, not 14.
4. Score the render against the anchor. Accept / hold / reject.
5. save_pair to keep the VRGDG-native layout.
```

**Step 3 is not optional.** When the reference key is wrong, VRGDG *deletes the
conditioning node* rather than erroring, and you get a normal text-to-image
render with no hint the reference was dropped. The node count is the cheapest
possible guard. (Key is `images` or `image_ingredients`, never `image_paths` —
see [vrgdg/traps](../vrgdg/traps.md).)

## Build it as a ladder, not a batch

This follows directly from our own [reference-collapse
measurement](what-we-measured.md): a reference is a **shot-family-local**
identity carrier, not a global one (0.932 matched, 0.301 medium, 0.493 wide).

So do not generate 40 images against one close-up anchor and hope.

1. **Write the quota table before generating anything.** Family → target count.
2. **Generate the close-up family first** — the anchor is strongest there, and
   it yields your highest-confidence images to promote.
3. **Promote within family:** the first image in a new family scoring ≥0.80
   against the close-up anchor becomes *that family's* anchor. If nothing
   clears 0.80, hand-pick rather than lowering the bar.
4. **Never let one family exceed ~40% of the set.** An over-represented family
   becomes the LoRA's default output framing.
5. **Record the family label per image** in `dataset.json`, so the composition
   is auditable and a retrain can rebalance rather than restart.

## Gate every save on ArcFace

**This is the piece VRGDG's Creator has no concept of, and we already have it
built and calibrated.** `lib/face_identity.py` — InsightFace `buffalo_l`,
CPU via onnxruntime, ~0.3 s/image, and completely independent of ROCm, so it
keeps working while the GPU is busy.

```
render -> faces_in() -> reject if != 1 face -> cosine vs anchor -> accept/hold/reject
```

- **Cache the anchor embedding once.** Do not re-embed it per candidate.
- **Log the score into `dataset.json` per item.** A dataset whose per-image
  scores you cannot see later is a dataset you cannot debug later.
- **Run `face_identity_stability()` on the final set** as a one-number
  acceptance test *before* spending an hour training.
- **Re-run the same measurement on images generated BY the trained LoRA.** Same
  instrument, before and after, is the only way to know training helped.

## The academic version, worth stealing the structure from

**"The Chosen One"** (SIGGRAPH 2024): generate a large batch, embed with
DINOv2, cluster with K-means++, keep the most cohesive cluster, personalise on
it, repeat until converged.

Its structure is worth copying; **its identity metric is worse than the one we
already have.** Adapted:

- Generate 60 images from the description alone, varied seeds, no reference.
- Embed with **ArcFace** (faces) *and* DINOv2/CLIP (whole-image look) — two
  matrices, not one.
- Cluster on the ArcFace embeddings; score clusters by mean squared distance to
  centroid.
- Take the most cohesive cluster — a principled alternative to "pick the image
  you liked", and it starts you with ~8 mutually consistent images.
- **Promote the cluster medoid, not the mean**, to be the Klein anchor.

scikit-learn is already in the ComfyUI venv.

## Deduplicate on two axes

A *generated* dataset's duplicates are not pixel duplicates. The real failure is
**near-identical poses from a repeated prompt** — PHash sees different pixels,
the trainer sees the same sample repeated, which is an unrequested repeat count.

1. PHash first (finds few on a generated set — itself informative).
2. Then a DINOv2/CLIP cosine pass; flag pairs >0.95 and review by eye. Sometimes
   the answer is to keep both and change one's caption.
3. **Replace what you delete, in the same shot family**, or the quotas rot.
4. **Dedup before captioning** — no reason to caption an image you will delete.

## Captioning: VRGDG's convention is backwards for characters

The standard character rule is [caption what varies, omit what is
constant](lora-training.md). VRGDG's Creator puts a fixed `trigger_phrase` into
every caption — **correct for the style LoRA it was primarily built for, and
exactly wrong for a character.** It teaches the trigger to mean a style, not a
person.

- **Keep** the `trigger_word` from `/vrgdg/lora_dataset/identity` — its
  constraints (7–20 ASCII chars, invented, not a dictionary word) are right.
- **Discard** the `trigger_phrase` from captions. Keep it as metadata and for
  inference prompts.
- **Strip identity invariants** from Florence-2 output before saving: face
  shape, eye colour, hair colour, age, build.

**Florence-2 runs today** — `microsoft/Florence-2-large` is already on disk
(1.55 GB) with the `comfyui-florence2` node installed. Caption once, store the
raw output, post-process — so the convention can change without re-running the
VLM.

## Diagnosing from the output instead of guessing at hyperparameters

Nearly every "my character LoRA is broken" report is a dataset defect.

| Symptom | Cause |
|---|---|
| every output is the same pose/framing regardless of prompt | shot-family imbalance, or undetected semantic duplicates |
| a background element you never asked for appears everywhere | it was constant across the set and never named in captions |
| identity high but prompt-following dead | overfit — take an earlier checkpoint, or lower LoRA weight at inference |
| identity never rises above the base model's own ~0.66 | **the dataset is the problem.** Do not retrain with different hyperparameters |

**Identity commonly peaks before the last checkpoint.** Save intermediates,
generate the same five validation prompts from each, and pick the peak.
