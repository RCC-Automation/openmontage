Filenames that lie — and one that lies about its architecture

darkBeast30BF16INT8 is not INT8; all 453 tensors are BF16, which also makes it trainable. gonzalomoXLFluxPony_v70PhotoXLDMD is a complete SDXL checkpoint that fails only because it sits in diffusion_models/. And gonzalomoXLFluxPony_v30FluxDAIO — named "Flux D", tagged Flux.1-dev — has zero guidance_in tensors, so ComfyUI drives it as schnell. Its own merge graph shows it is 30% gonzalomoChroma_v30: the AIO and Chroma are not independent samples and must not both be scored as separate models.

Both Z-Image GGUFs are dead weight

The constraint is system RAM, not VRAM — and it crashed the backend

This machine reports ~88 GB of "VRAM", but that is the unified pool as the GPU sees it. Actual system RAM is 63.6 GiB, ComfyUI runs with --disable-mmap so every load is a full read into RAM, and fp8 weights are upcast to bf16 here because supports_fp8_compute() is false on gfx1151. Loading the 17 GB all-in-one on top of a resident flux1-dev (23.8 GB) plus t5xxl (9.3 GB) killed the ComfyUI process outright. Run the heavy Flux files alone, cold, and flush between them — and note that POST /free releases ComfyUI's cache but not the process's RSS: free RAM fell 45.5 → 22.3 → 19.6 GiB across three flushed runs.

Retracted — the CLIP-skip finding was wrong

This page previously said the bundled SDXL graph had no CLIPSetLastLayer, so every SDXL render ran at clip skip −1 and three checkpoints had never been driven correctly. That was wrong. Measured by pixel hash: a render with no node, a render at −2, and the original graph are all pixel-identical — ComfyUI's SDXL default already equals −2. Those three checkpoints were being driven correctly all along.

What is true, and sharper: adding the node at −1 renders a pure black frame on babesIllustrious, realismIllustrious and MoP v7.1 — mean luma 0.00, reproduced across three seeds each. −1 is not "no skip" for SDXL; it forces the true final CLIP layer, which is degenerate in those three merges. The new binding therefore leaves the node out of the graph unless a skip is explicitly asked for.

Mis-driving is now confirmed on two families

z_image_base_bf16 run at the Turbo recipe comes out blonde, waxy and painterly — it reads as a broken model. At its own recipe (25 steps, cfg 4, real negative) it produces the best single frame of the entire session. Same file. This is the DECISIONS #24 lesson reproducing exactly, and it is why the benchmark must carry a per-model recipe rather than one global setting.

Chroma's whole selling point is switched off at its own recommended settings

Chroma exists because it restores real classifier-free guidance to a schnell-derived model — working negative prompts. But its author recommends cfg 1.0–1.3, and at cfg 1.0 ComfyUI never evaluates the negative branch at all. Measured both ways: the stock recipe (26 steps, cfg 3.5, negatives live) is visibly richer and more detailed than the author's 12-step cfg-1 recipe, for 1.8× the time. If you reach for Chroma, reach for it at cfg > 1 or don't bother reaching.

Getting the best out of what you have

In order of return per unit of effort. The first four cost minutes and change results immediately.

  1. Hardlink gonzalomo v70 into checkpoints/ — done

    Same volume, zero bytes, one command. A seventh SDXL candidate and the newest DMD of the three. ComfyUI now lists 12 checkpoints.

  2. Leave CLIP skip alone unless you mean it — done

    clip_skip is now an opt-in binding on comfyui_image, and the node is excised from the graph when no skip is requested — so the default path is pixel-identical to what it always rendered. Use it only for deliberate excursions to −3 or −4, which one installed author varies for effect.

  3. Run Klein distilled at 4 steps, not VRGDG's 8-step dpmpp_sde

    10.6 s instead of 28 s for equal or better output. Klein is nearly three times cheaper than the project has been assuming, which changes where it belongs in the film pipeline.

  4. Drive the three DMD checkpoints at their embedded recipes

    Already implemented in infer_sampler_recipe — 10/11/13 steps at CFG 1, lcm. They become the fastest good models on the machine at 10–20 s.

  5. Stop paying for things that do nothing

    Skip on Klein: FluxGuidance, AuraFlow shift, and 50-step Base (129.5 s buys nothing visible over 20-step's 58.9 s). Skip on SDXL: the refiner stage, FreeU, SAG, and the sdxl-vae-fp16-fix download. Each of these is in a community workflow somewhere; none earns its place here.

  6. Vary the seed between benchmark cells

    ComfyUI returns a cached result for an identical graph — 2.0 s instead of a render. A harness that doesn't vary the seed will record fictional timings that look like a breakthrough. This one bit me today.

  7. Move Z-Image off the VRGDG two-pass route for stills

    The standalone single-pass graph renders in 14.1 s warm (n=5 across two Turbo files), and the graph is ComfyUI's own blueprint rather than something we invented. The VRGDG route logs a 60.6 s median, but it renders 1280×720 and then again at 1920×1080 — about 2.7× the pixels plus a second pass — so treat that as a different job, not a 4× saving. For a single-pass still at 1280×720 the standalone graph is the cheaper instrument.

  8. Run the heavy Flux files alone, and never back to back

    System RAM is the binding constraint at 63.6 GiB with --disable-mmap. Order the benchmark so flux1-dev and the 17 GB all-in-one never share residency, and flush between them. Ignoring this is what took the backend down mid-run today.

How the benchmark gets built

The design follows from one fact in the matrix above: the axes are per-family. A single global grid would be mostly empty cells — Klein has no LoRA column, SDXL has no encoder column. So the structure is a fixed common scene every model renders, plus a knob strip per family that only varies what that family can vary.

The shape

  • One API-format JSON per family in workflows/image-bench/, with titled Primitive nodes for prompt, seed, size and steps. This file opens directly in ComfyUI for your hand experiments and is what I drive in batch — one source, no divergence. Proven today: the Klein graph I built rendered on the first submission.
  • One binding profile per graph, in the format tools/_comfyui/profiles/ already uses. This needs no new tool — comfyui_image already accepts workflow_path + workflow_profile_path, and the validator fails loudly if you edit the graph in a way that breaks a binding.
  • Registry drivers for flux1, chroma and Z-Image GGUF, so those six files stop being excluded. They're refused today by our own code, not by the machine.

The scene, held fixed across everything

Seven prompts at 1280×720 (the film's frame, a multiple of 16, inside every family's native band), one shared seed. The prompts stress capabilities that fail differently: photoreal face, hands and full body, wide environment with named lighting, text in image, multi-subject attribute binding, a stylised illustration, and one long constraint-heavy prompt that tests encoder capacity.

One wrinkle worth deciding deliberately: the Illustrious and Pony checkpoints want booru tags, everything else wants prose. Sending one dialect to all twenty measures our ability to mis-drive half of them. The fix is to author each prompt in both dialects, run the tag families on both, and score adherence against the single shared intent — so the dialect effect is visible on the sheet rather than hidden in it.

What the machine scores, and what it doesn't

Print only the calibrated axes: the technical gate (and only when it fails), CLIP prompt adherence within a prompt row, and wall-clock split into cold load and warm render. Do not print the weighted casting total — those weights were built for casting one character, not for comparing capability — nor identity or look-consistency on single-seed cells. The ranking narrows; you decide.

Order every run by model, not by prompt. Loading a model costs 20–40 s and ComfyUI accumulates loaded models until memory pressure evicts them — reordering is the difference between the quick tier taking 28 minutes and taking an hour.

Where I'd start

Phase 1 is now mostly done. All five family graphs have been built and proven by rendering — they exist as working API JSON and need only to be committed to workflows/image-bench/ with their binding profiles. That was the riskiest assumption in the plan and it held.

Phase 0 remains, and it is an afternoon: registry drivers for flux1 and chroma, the seed-variation guard, and a model-ordering rule that keeps the two heavy Flux files apart. The v70 hardlink and the clip_skip binding are already done. Then the quick tier runs and you have an eighteen-column contact sheet.

The open question is no longer which models work — it is which of them you actually want. That is the part the machine does not decide.
